 P0 · 출시 준비 — 지금 제일 위
═══════════════════════════════════════════════════════════════════════════
라이선스가 먼저였던 이유는 나머지 둘이 그걸 따라가기 때문이었고 — dmg 안의
EULA, About/Welcome 문구 — 그건 이제 정해졌다. 남은 둘 중에서는 dmg 가 먼저다:
업데이트 UI 가 가리킬 대상이 dmg 이고, 서명·노터라이즈는 P3 컴포넌트까지 막고 있다.

✅ 1. 라이선스 = source-available     **결정 완료 (2026-08-18). 법적 변경 없음.**
      충돌은 실체가 아니라 표현이었다. `LICENSE` §10 이 이미
      "This is a source-available licence. It is not an open-source licence"
      라고 적고 있고, 조건도 이미 개인·비상업 무료 / 상업 이용은 별도 계약이다.
      어긋나 있던 건 **요약문**뿐 — 한국어 요약과 정책 문서만 "클로즈드 소스"를
      머리말로 달고 있어서 자기 본문과 반대로 읽혔다.
      · 고친 것: 그 두 머리말을 본문에 맞춤. **영문 조항은 손대지 않았다.**
      · "오픈소스"라고 부르지 않는 이유는 OSD 6조와 양립하지 않기 때문이고,
        그건 §10 이 이미 명시하고 있다.
      · 남은 것: About/Welcome 문구가 라이선스를 뭐라고 부르는지 확인.

◐ 2. 배포 = 서명 없이 "그래도 열기"    **결정 (2026-08-18).**
      신뢰하는 소수에게만 먼저 준다. GitHub 배포물 상당수가 이렇게 한다.
      · 무료 계정으로는 Developer ID 인증서도 노터라이즈도 없다 = Gatekeeper 가
        보는 그 둘이 없다. 받는 쪽은 시스템 설정 → 개인정보 보호 및 보안 →
        "그래도 열기" 를 한 번 거친다(Sequoia 부터 우클릭 우회는 사라졌다).
      · 그래서 **P3-21 컴포넌트 다운로드는 계속 막혀 있다.** hardened runtime 의
        library validation 은 받아서 dlopen 하는 dylib 에 같은 팀 서명을 요구한다.
        UI 는 만들 수 있고 만든다 — 받아서 로드하는 부분만 계정 뒤에 있다.
      · 남은 것: dmg 레이아웃(배경·/Applications 링크), 그리고 받는 사람에게 줄
        한 문단짜리 첫 실행 안내. 계정이 생기면 스크립트에 `--sign` 자리만.

◐ 3. 업데이트 UI 를 애플답게     **1차 완료 (2026-08-18).**
      기준은 시스템 설정 → 일반 → 소프트웨어 업데이트. 거기서 가져온 세 가지:
      · **행에 색 글리프를 안 쓴다.** 애플의 색 둥근사각 아이콘은 **사이드바** 것
        — 서른 개 목록에서 페이지를 찾는 수단이다. 페이지 안의 행은 제목·값·ⓘ
        뿐이고, 거기서 색은 이미 보고 있는 것을 꾸미는 일이다. 파란 시계와 주황
        망치를 뺐다.
      · **막는 사실은 각주가 아니라 상태 줄이다.** "다운로드할 수 없음" 이 제목
        바로 밑 빨간 줄에 있고, 그 해법은 자기 행과 자기 버튼을 갖는다. 우리는
        같은 문장을 섹션 푸터에 두고 있었다 — 버튼이 왜 소용없는지가 아니라
        면책 문구처럼 읽혔다.
      · **끝에 붙는 건 ⓘ 지 chevron 이 아니다.** 이 행들은 파고드는 게 아니라
        설명한다.
      남은 것: dmg 가 생기면 "Open Release…" 가 GitHub 대신 그걸 가리켜야 한다
      = P0-2 뒤.

✅ 단축키 변경                   **완료 (2026-08-18).**
      없던 것은 버튼이 아니라 **정체(identity)** 였다. 페이지는 Swift 안의 손으로
      쓴 문자열 열여섯 개(`("Save", "⌘S")`)였고, 아무것과도 연결돼 있지 않아서
      틀릴 수조차 없었다 — "Save" 라는 행과 실제로 저장하는 키를 잇는 것이 없었음.
      그리고 실제로 틀려 있었다: "Terminal in Editor Pane ⌃⇧T" 라고 적혀 있는데
      그 메뉴 항목은 줄곧 ⇧⌘T 였음.
      · `core/keymap.rs` — 명령마다 id·제목·그룹·기본 코드. 사용자 변경분은
        `Config.keybindings` 에 **다른 것만** 저장(기본과 같으면 줄을 안 남김).
        전역 설정이지 프로젝트가 아님 — 단축키는 읽는 사람 것.
      · 규칙: 수식자 순서·대소문자는 표현이라 같은 코드로 취급 · **⌥+글자는
        거부**(맥에서 ⌥R 은 ® 라 메뉴가 가져가면 모든 텍스트 필드에서 그 문자를
        뺏김) · 설정 전에 **충돌을 이름으로 알려줌**(AppKit 은 같은 키가 둘이면
        조용히 하나를 고른다) · 못 읽는 override 는 무시하고 기본으로(손으로 고치는
        파일이므로 오타 하나가 Save 를 못 쓰게 만들면 안 됨).
      · **카탈로그 = 실제로 배선된 메뉴 명령 33개**, 그 이상도 이하도 아님.
        메뉴가 안 읽는 행은 페이지가 못 지키는 약속임. ⌃T·⌃⇥ 는 코어의 키라
        일부러 뺐다(모달 키맵은 별개 기능).
      · 녹화는 `NSView.performKeyEquivalent` 에서 — 메뉴보다 **먼저** 받아야
        ⌘S 를 녹화할 수 있음. 녹화 중일 때만 가로챈다.
      · 메뉴가 표를 읽게 함(`suiseiShortcut`). App 은 engine 을 `@StateObject` 로
        안 잡으므로(d8afc22 — 그러면 타건마다 메뉴바가 재빌드됨) `suiseiCommands`
        는 한 번만 평가된다 → 메뉴마다 `Keyed` 로 감싸 **`KeymapState` 하나만**
        관찰하게 했다. 재바인딩이 재시작 없이 반영된다.
      테스트 16개(코어 13 + 설정 파일 왕복 3) + ABI 레이아웃 1.

═══════════════════════════════════════════════════════════════════════════
 알고 안 고침
═══════════════════════════════════════════════════════════════════════════
✋ Run/Build 콘솔이 stdin 을 안 준다.
   입력을 기다리는 프로그램은 터미널에서 돌려야 한다.

✋ 문제 목록은 **마지막 한 번의 실행** 것이다.
   새 실행이 이전 진단을 지운다 — 의도한 것(어제의 물결선은 오늘의 답이
   아니다)이지만, 실행 사이에 파일을 고치면 낡은 물결선이 잠깐 남는다.
   LSP 가 같은 줄을 이미 말하고 있어서 실제로는 잘 안 보인다.

✋ refresh_syntax 가 버전마다 워커에 넘기는 전체 텍스트 스냅샷.
   **릴리스에서 키당 0.101ms(그중 스냅샷 0.081ms)** = 120fps 프레임 예산의 1.2%.
   예전 기록의 1.99ms 는 디버그 빌드 숫자였다. 편집만 보내는 설계는 여전히
   타당하지만, 지금 하면 측정되지 않은 이득을 위해 core 와 워커가 텍스트에
   대해 서로 다르게 알 수 있는 상태를 새로 만드는 거래가 된다.

✋ `.js` 파일의 멀티메가바이트 한 줄은 tree-sitter 파스 자체가 2초 걸린다.
   쿼리는 480열에서 멈추게 고쳤다(8MB 17.4s → 2.0s). 남은 2초는 진짜 파싱이고
   문법 워커 스레드에 있어서 UI 는 안 멈춘다.
