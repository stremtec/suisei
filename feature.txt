✅ 3. Setting ui 개선{
    Account 쪽 이외에도 여러 부문에서 UI가 '애플답지 않음.' 애플 네이티브 버튼이나 제질을 안쓴게 좀 많은듯?

    → 기준을 Xcode 설정창으로 잡음(사용자 지적). 처음엔 시스템 설정 쪽으로 갔다가
      되돌림 — 사이드바는 컬러 타일이 아니라 라벨과 같은 색의 모노크롬 글리프.
      컬러 타일은 Xcode 에서 '페이지 안의 이동 행'에 씀(Editing ▸ Display 등).
      그래서 SettingsNavigationRow 로 옮김.
    → Save 바 제거. 시스템 설정엔 저장 버튼이 없음. Core 가 행을 갖고 있어서
      매 변경마다 쓰면 설정 파일을 키 입력마다 다시 쓰는 게 이유였는데, 그건

      취소·재시작해서 색상환을 드래그해도 최종값만 한 번 씀.
    → Shortcuts 페이지: 손으로 그린 키 칩 2열 그리드였음. 키가 먼저 오니까
      정작 눈으로 찾는 열("Save")이 못 찾는 열이었음. 필터 + 명령 왼쪽 /
      키 오른쪽 정렬로. 메뉴 막대가 쓰는 순서.
    → Appearance 가 액센트를 두 번 물었음(원 스트립 + "Custom Accent Color" 행,
      Default 버튼도 두 개). 한 줄로, 커스텀 웰은 스트립 끝에.
    → Account 페이지는 손 안 댐 — "Account 쪽 이외에도" 라고 하셔서.

✅ 10. 왼쪽 사이드바 git ui 개선 {
    제목과 같음.

    → 파일 행을 소스 리스트로 다시 짬. 전에는 상대 경로 전체를 monospace 로
      가운데 잘라서 보여주고 상태 글자를 앞쪽 열에 맨몸으로 뒀음 — 240pt 열에서
      찾는 게 파일명인데 정작 생략되는 게 그 부분이었음. 이제 아이콘 · 이름 ·
      폴더(뒤에 흐리게, 앞에서 자름) · 오른쪽 상태 칩. 루트 파일이면 폴더 생략.
    → 히스토리가 Text(g.line) 이었음 — FFI 가 "{strip} {short} {subject} {when}"
      으로 미리 이어붙인 문자열. 커밋이 경계에서 눌려서 face 에 재료가 없었음.
      short/subject/when/refs/lane color 를 따로 건네고 레인 색 점 + 제목 +
      해시·날짜·refs 로 그림. subject 가 compositor 에서 56자로 잘리고 있기도
      했음(자리가 있어도 못 보여줬다는 뜻).
    → 그래프 스트립은 네비게이터에 일부러 안 그림 — 모든 행이 monospace 로
      정렬돼야 그래프로 읽히는데 240pt 가 그걸 제목과 동시에 못 줌.
    → 미푸시 커밋 목록(Xcode 의 U 배지) 넣음. 계획은 "위 ahead 개에 배지"였는데
      그게 틀렸음 — 사이드바 워크가 git log --all --date-order 라, 한 시간 전에
      푸시된 동료의 팁이 내가 안 푸시한 두 커밋 위에 앉음. ahead 는 세지, 지목하지
      않음. 그래서 core 가 답이 이름 목록인 질문을 함: git rev-list @{u}..HEAD.
      GraphRow.unpushed 가 개수가 아니라 행마다 ABI 를 건넘 — face 가 틀릴 규칙
      자체가 없게. 업스트림이 없으면 rev-list 가 실패하고 아무것도 안 찍힘(= ahead
      가 그 브랜치에 대해 이미 보고하는 답).
      History 헤더는 찍힌 행 수를 셈. 커밋을 세면 그래프 limit 을 보고하는 건데
      그건 설정임.
}

⚠️ 11. 깃 워크벤치 에니메이션 끊김 등 이슈 개선 {
    제목과 같음.

    → 사이드바 열림 애니메이션의 "중간에 툭" 은 해결. 세 번 틀리고 네 번째에
      계측으로 잡음. 순서대로:
      · TravellingPill 이 네 값을 다 애니메이션 — 이산 토글엔 맞지만 사이드바
        접힘은 폭이 연속으로 쓸려서, 매 프레임 새 보간을 시작함(애니메이션이
        애니메이션을 쫓음). 진짜 문제는 아니었지만 실제 결함이라 고침.
      · 사이드바 라벨들에 lineLimit 없음 → 좁을 때 두 줄로 감기고 풀리면서
        아래가 다 올라옴. 이것도 실제 결함, 이것도 아니었음.
      · SwiftUI GeometryReader 로 쟀는데 분할 애니메이션은 AppKit 것이라
        중간 프레임이 안 보임. **틀린 층을 재고 있었음.**
      · layer.presentation() 을 디스플레이 링크로 찍으니 바로 나옴:
          pane0=[x-144 w288] pane1=[x-144 w1328]
          pane0=[x0    w288] pane1=[x0    w1328]
          pane0=[x0    w288] pane1=[x0    w1040]
        분할 뷰가 1328(=1040+288)로 부풀어 좌우 144씩 창 밖으로 나갔다가
        마지막 두 프레임에 튕겨 돌아옴. 원인은 frame(minWidth: 1040) —
        SwiftUI 프레임으로 쓴 최소폭은 콘텐츠가 *요구할 수 있는* 폭이라
        사이드바가 열리면 사이드바+디테일최소를 요구함. 창의 contentMinSize
        로 옮김. 닫을 때 멀쩡했던 건 더 넓은 공간을 요구할 일이 없어서.
      · 사이드바 구조도 safeAreaBar 로 바꿈(List 가 열을 소유). VStack 에
        rail 을 얹으면 상단 safe area 주인이 둘이라 패스마다 답이 갈림.
    → SUISEI_DIAG=sidebar 로 프레임 단위 계측이 남아 있음(꺼져 있으면 비용 0).
    → 남은 것: 워크벤치의 다른 애니메이션(모드 전환 등)은 미확인.
}

    유지 — 아무도 안 기다리고, 바운드가 메모리 바운드임(prewarm 마다 파일 전체 텍스트).
    take 는 한 번에 한 단위, parse 먼저. 큐를 배치로 다 비우면 라이브 문서가 다시
    같은 2.4MB 뒤에 서게 되고, 채널 대신 큐로 바운드된 같은 대기임.
  ✅ WAL 이 메인 틱에서 fsync — 해결. 쓰기 스레드가 디렉터리를 소유함. 틱은 언제
    flush 할지만 정하고 스냅샷을 넘기고 돌아옴. 헤더를 본문과 따로 써서, 짧은 6줄
    붙이려고 문서 전체를 한 번 더 복사하던 format! 도 없앰.
    잡은 WAL 경로로 키를 잡고 새 잡이 대기 중인 걸 대체 — 큐 메모리가 flush 당
    하나가 아니라 더티 파일당 하나. on_saved 도 같은 큐로: 틱에서 지우면 아직
    대기 중이던 쓰기가 나중에 착지해서 이미 저장한 파일을 복구 제안하게 됨.
    닫을 때 버리지 않고 드레인하고 Drop 이 join — 더티인 채로 종료하는 게 바로
    이게 중요한 순간.
  ✅ 벤치마크 자체가 틀린 답을 줌 — 해결, 그리고 고치자마자 뭔가를 찾음.
    · 콜드 엔진에 타이핑 → 트리 없는 에디터를 재고 있었음. flush_syntax 로 워밍.
    · Enter 를 gui_type_char('\n') 로 → 타이핑 빠른 경로에 개행을 넣는 것이라
      스마트 Enter 를 통째로 건너뜀. dispatch_key 로 진짜 Enter.
    · 6k 에서 멈춤 → 20k 까지. 감사가 인용한 두 회귀가 다 20k 숫자였음.
    · assertion 없음 → 일반 pass 에서 도는 가드 테스트 추가.
    · 생성기 자체가 O(n²) 였음(s.lines().count() 가 루프 조건). 그래서 아무도
      말이 되는 크기로 안 돌려봤던 것.
    가드가 즉시 실패: 파일 10배에 키 8.5배. 컴플리션에 O(파일) 패스가 둘 더 있었음 —
    아래 참조. 가드는 워커 스냅샷을 빼고 비교함. refresh_syntax 가 버전마다 전체
    텍스트 사본을 워커에 넘기는 건 의도된 O(파일)이고(비동기 파스는 안 움직이는
    스냅샷이 필요함), 20k 에서 키당 1.99ms 중 1.75ms 임. 그냥 비율을 재면 그 복사만
    재는 거라, 옆에 새 O(파일) 패스가 생겨도 계속 통과함.

  ✅ (가드가 찾음) 컴플리션에 O(파일) 패스 둘
    · symbols_in_scope_at_caret 이 캐럿 바이트 오프셋을 찾으려고 text.lines() 를
      맨 위부터 훑음. gui_edit.rs 주석이 28.5ms/키 의 절반이라고 이미 지목한 그
      스캔인데, 주석이 설명하는 고침은 팝업이 이미 떠 있는 경우만 커버함 — 모든
      식별자의 첫 두 글자는 여전히 훑고 있었음. GlobalScopeCache 에 줄 색인,
      트리로 키(텍스트와 트리는 같이 움직임) → 키당이 아니라 초당 몇 번.
    · visible_at 이 캐시된 전역 목록을 clone(20k 에서 String 2,500개)하고, 8개
      보여주려고 보이는 이름 전부에 ScopeSymbol 을 만듦. 이제 빌려 쓰고, prefix 를
      내려보내서 매치 불가능한 심볼은 아예 안 만듦. 권위 있는 필터링은 여전히
      activate_with — may_match 는 할당만 피하면 되니 일부러 느슨하고 non-ASCII 는
      다 통과시킴.
    키당 컴플리션 2.67ms → 0.227ms (20k, unopt).

실시간 협업 설계 (위 **feature** 1번의 답) — 요지:
  · gh 로그인과 Suisei Cloud 로그인을 UX 는 한 화면, 인증은 완전 분리.
    gh 는 로컬 개발 도구고 권한이 훨씬 넓음. Cloud 로그아웃이 gh auth logout 을
    부르면 안 됨.
  · project.suiseiprj 에 멤버를 적지 말 것 — 파일 고쳐서 자기 권한 올릴 수 있고,
    merge conflict 로 꼬이고, GitHub username 은 바뀜. 파일엔 project_id 만.
    권한의 정본은 서버.
  · 역할 Owner / Admin / Editor / Viewer. "Hand over admin" 은 역할이 아니라
    소유권 이전 액션. Admin 은 자기보다 낮은 역할만 관리.
  · 서버는 역할이 아니라 capability 로 검사 (document.write, member.invite …).
  · presence: 편집은 즉시·순서보장·ACK, 마우스는 움직일 때만 8~12Hz latest-only,
    300ms 멈추면 중단. 받는 쪽에서 80ms jitter buffer + 120fps 보간.
  · 좌표는 화면 픽셀이 아니라 문서 기준 (byte_offset + affinity + at_revision).
  · 편집 채널과 presence 채널 분리, 큐 우선순위 edit > control > presence.
  · 불변식: 키 입력은 GitHub·인터넷·서버 ACK 를 절대 기다리지 않는다.

· suisei-daemon 의 two_windows_aggregate... 테스트가 간헐적으로 실패.
  깨끗한 트리에서도 실패하는 기존 flake.
· suisei-core 의 dap::tests::free_port_and_wait_helpers 가 병렬 부하에서 간헐 실패.
  포트 경합. 단독으로 돌리면 깨끗한 트리에서도 이 트리에서도 항상 통과.
· 남은 키당 O(파일): refresh_syntax 가 버전마다 워커에 넘기는 전체 텍스트 스냅샷.
  20k 에서 키당 1.99ms 중 1.75ms. 의도된 것 — 비동기 파스는 자기 밑에서 안 움직이는
  스냅샷이 필요함 — 이지만, 워커가 이미 자기 last_text 로 증분 파스를 하니까
  편집만 보내는 건 가능함. 아키텍처 변경이라 이번엔 안 함.

✅ 상태바가 텍스트 아닌 페인에서도 "Ln 1, Col 1 · No Wrap" — 해결. 줄이 없는
  문서에 대한 세 가지 사실이었음: 앉을 줄도, 꺼져 있을 랩도, 몇 %인지 셀 줄도 없음.
  바 오른쪽 끝이 무조건이었던 것. core 는 페인 kind 를 계속 갖고 있었고 바가 물어본
  적이 없었음. 셸은 아무 말 안 함(왼쪽 포커스 칩이 이미 말하고, 그 안 캐럿은 거기
  도는 프로그램 것). 뷰어는 자기가 뭔지 + 툴바가 이미 보여주는 페이지·줌.

✅ 랩 + 탭 줄 클릭 캐럿 어긋남 — 해결. face 는 *건네받은* 문자열에 대고 재는데
  그건 expand_tabs(raw, tab_width) 임. '\tfn main()' 의 f 를 누르면 오프셋 4(펼쳐진
  들여쓰기 4칸)를 보고함. 원본 줄에서 읽으면 그건 네 글자 안쪽 — 탭 하나와 글자
  셋 — 이라 답이 버퍼 4열의 화면 열, 즉 줄 끝이 됨. 들여쓴 줄의 모든 클릭이
  빗나갔고 들여쓰기가 깊을수록 더 멀리. 랩 이전부터 있던 게 맞음: 그리기용으로 탭을
  펼친 순간부터 두 문자열이 달랐음.
  이제 같은 방식으로 펼치고 셀 폭을 더함 = 화면 열 그 자체(펼친 텍스트가 곧 화면
  행이라 되돌릴 게 없음). Buffer 의 두 열 변환이 탭 스톱 4를 하드코딩하고 있던 것도
  같이 고침 — 컴포지터는 app.tab_width 로 펼치니까 다른 설정에선 서로 달랐음.
