 P2 · 제품의 격을 정하는 것
   ✅ 에디터 캔버스 접근성  **완료.** 캔버스가 이제 VoiceOver 에 텍스트 영역임.
       · 텍스트 영역은 **문서 전체를 문자 오프셋으로** 물어봄. 문서는 core 에
         있으니 face 가 사본을 들지 않고 **core 에 물음**(ax_line_count /
         char_count / line / offset_of_row / row_of_offset / selection).
         사본은 타건마다 맞춰야 할 물건이 하나 더 느는 것이고, 조용한 에디터보다
         **낡은 줄을 읽어주는 에디터가 더 나쁨.**
       · 오프셋은 **문자**지 바이트가 아님. 그리고 마지막 줄 뒤엔 개행이 없음 —
         이 둘이 틀리면 줄마다 1씩 밀려서 아래로 갈수록 엉뚱한 데를 읽음
         (테스트가 잡음).
       · **읽기만 아니라 조종도 됨**: VoiceOver 는 선택 범위를 *설정*해서
         이동함. 캐럿을 보고만 하는 에디터는 읽히지만 몰 수는 없음.
       · 알림은 **캐럿이 실제로 움직였을 때만**, 그리고 모든 이동 경로가 모이는
         한 곳에서(타이핑·클릭·⌘G·정의로 이동·디버거 정지). 경로마다 붙이면
         맞춰야 할 목록이 되고, 60Hz 로 "바뀜" 을 쏘면 자기 말을 자름.
         VoiceOver 가 꺼져 있으면 아무 일도 안 함.
       · `accessibilityHelp` 이 **캐럿 줄의 진단**을 먼저 말함 — 물결선은 읽는
         사람에게 안 보이고, 그 줄에 대해 에디터가 아는 것 중 제일 유용함.
       · 큰 파일은 `accessibilityValue` 가 보이는 구간만 줌(줄 단위 이동은 범위
         API 를 타니 파일 전체가 그대로 열림). 한계는 말해줌.
   ✅ Run / Build 통합            **완료** (2026-08-18)
       핵심 한 줄: **컴파일 에러는 진단이다.** 예전엔 `first_compile_error` 가
       stderr 에서 첫 `error:` 와 화살표 줄을 이어 붙여 문장 하나를 띄웠음 —
       파일과 줄 번호를 말하면서 거기로 갈 방법이 없고, 나머지 스무 개는 버림.
       · `build.rs` 신설. `plan` 이 매니페스트를 보고 Build/Run/Test 가 여기서
         무엇인지 정함(cargo·swift·go·npm·make·단독 스크립트). 프로젝트가 다르게
         말할 수 있음 — `project.suiseiprj` 의 `settings.commands`.
       · 파서 둘. `cargo --message-format=json` 은 스팬을 그대로 주고, 나머지
         컴파일러가 찍는 글자는 네 모양으로 읽음: `path:line:col: severity: msg`,
         tsc 의 `path(line,col):`, rustc 의 두 줄짜리 사람용, 파이썬 트레이스백.
         그리고 러스트 패닉 — 실패한 테스트 출력에서 제일 쓸모 있는 줄인데
         컴파일러 메시지가 아니라서 아무도 안 읽고 있었음.
       · Problem 은 **경로가 붙은 Diagnostic**. 에디터엔 이미 물결선도, 목록도,
         `]d` 도 있음. 자기만의 종류로 오면 물결선도 목록도 키도 따로 만들어야
         하고, 읽는 사람이 "어느 밑줄이 어느 것" 을 배워야 함. `App::diagnostics`
         가 두 출처를 한 줄기로 잇고, 그리는 쪽·세는 쪽·도는 쪽이 전부 거기에
         물어봄.
       · 프로세스는 스레드 둘이 바이트만 나르고 **파싱은 메인 스레드에서 한 줄씩**.
         그래서 파서 테스트가 컴파일러 대신 문자열로 돌아감.
       · 바닥 독의 세 번째 탭. 왼쪽에 문제(=답), 오른쪽에 콘솔(=근거). 문제가
         없으면 콘솔이 전부 — "문제 없음" 이라고 적힌 빈 칸을 출력 옆에 세우는
         건 중요한 게 있어야 할 자리에 아무것도 없는 것.
       · ⌘B / ⌘R / ⌘U, 그리고 패널은 **상태를 따라** 올라옴(메뉴로 눌러도
         패널에서 눌러도 같은 곳에 도착).

✅ 2. Account 기능 완성{
    현재는 너무 불안정함. gh를 제대로 찾지 못함.

    → gh 는 멀쩡했고 Suisei 가 못 봤음. Finder 에서 띄운 앱은 Finder 의 PATH
      (/usr/bin:/bin:...)를 물려받아서 Homebrew 가 없음. rg, rust-analyzer,
      cargo 도 같은 병이었음. b30da36
    → 두 가지 실제 결함을 찾아 고침(재현 없이 코드 감사로):
      · 계정 fetch(인증 상태·프로필·캘린더)와 사용자가 고른 기여도 연도가 수신자
        슬롯 하나를 공유. 나중에 시작한 쪽이 앞쪽 수신자를 바닥에 떨어뜨림 —
        고아가 된 스레드의 send 가 조용히 실패하고 답이 영영 안 옴. 계정 fetch 의
        답은 loading 을 끄는 유일한 것이라, 초상화 아래 스피너가 세션 내내 돌고
        멈출 방법이 없었음. 흔한 순서임: 연도 피커가 고를 연도를 갖게 되는 시점이
        바로 프로필이 도착한 때고, 그때 그 fetch 는 아직 캘린더를 마치는 중.
        슬롯 둘 + adopt() 하나로. 캘린더 하나가 실패한 건 "Could not reach
        GitHub" 가 아니고 loading 을 건드릴 일도 아님(옆의 프로필은 멀쩡히 최신일
        수 있음). 이미 옮겨간 연도의 캘린더는 그리지 않고 버림.
      · 아바타 디스크 캐시가 한 번도 적중한 적이 없었음. 파일명이
        String(url.absoluteString.hashValue) 인데 Swift 는 Hasher 를 프로세스마다
        랜덤 시드로 잡음 — 실행마다 이름이 달라서 매번 네트워크로 다시 받고 매번
        새 파일을 남김. 이 머신에서 측정: 84개, 15MB, 그중 실제 이미지는 2종.
        FNV-1a 를 직접 씀(요구사항이 정확히 '안 바뀌는 것' 이라, 표준 라이브러리가
        재시드하거나 재조정할 수 있는 해시는 같은 버그를 예쁘게 쓴 것). TIFF →
        PNG (176KB → 약 20KB). 옛 확장자 없는 파일들은 폴더를 처음 만질 때 한 번 쓸어냄.
        실패한 fetch 는 이제 자기가 뭘 받던 중이었는지 잊음 — 요청 한 번 끊기면
        앱을 재시작할 때까지 초상화가 안 나왔음(loadAvatar 맨 위 가드가 계속
        "그거 이미 하는 중" 이라고 답해서). 우리가 취소한 경우는 제외 — 더 새 URL 이
        이미 날아가 있고 그걸 되돌리게 됨.
    → 남은 것: 로그인 플로우 자체는 재현이 없어 손대지 않음. gh auth login 대기

✅ 9. DAP 완전구현 {
    제목과 같음.

    → 먼저 읽어봤더니 "DAP 를 구현" 하는 일이 아니었음. suisei-core/src/dap.rs 가
      2,995줄짜리 완성된 DAP 클라이언트임 — launch, pid/port attach, node,
      continue, step over/into/out, pause, stop, restart, evaluate, 프레임 선택,
      변수 확장, 조건부 브레이크포인트, logpoint, 브레이크포인트 영속화,
      .vscode/launch.json 까지. 그런데 `grep dap suisei-engine/src/ffi.rs` 가
      **0건**. TUI 가 직접 몰았고, 이제 유일한 face 인 Mac 앱은 브레이크포인트
      저장소 말고는 아무 데도 못 닿았음. 즉 디버거는 있는데 쓸 방법이 없었음.
      이번 세션 내내 나온 그 패턴("core 가 가진 게 ABI 를 안 건넘")의 최대 사례.
    → 다리를 놓음. 스냅샷 하나(상태·어댑터·상태줄·스레드·프레임·평탄화된 변수
      트리·콘솔 꼬리·정지 위치) + 명령. 명령은 raw 클라이언트가 아니라 App 의
      dap_* 레이어로 감 — GUI 가 TUI 가 가던 길을 그대로 가게.
    → fingerprint 로 게이팅. 구조체가 10만 바이트대고 fingerprint 는 u64 임.
      diagnostics_fingerprint 가 이미 같은 이유로 있음. 개수·선택·위치에 더해
      **각 행의 expanded 플래그**도 섞음 — 변수를 펼치면 길이는 그대로인 채
      트리가 바뀌므로 길이만 보는 fingerprint 는 그걸 놓침.
    → 콘솔은 core 의 400줄 중 최신 200줄을 나르고 진짜 총 개수를 같이 보냄.
      가장 오래된 200줄을 날랐으면 세션이 시작한 자리만 영원히 보여줬을 것.
    → 명령 11개가 export 하나로. 인자가 없고 전부 "이 세션에 이걸 해라" 임 —
      비슷한 extern 11개는 널 체크를 빠뜨릴 자리 11개.
    → 패널은 Xcode 배치: 위에 트랜스포트, 콜스택과 변수를 나란히, 아래 콘솔.
      셋이 서로 다른 질문에 답함(나 어디 있나 / 뭐가 스코프에 있나 / 뭐라고 했나).
      Start 와 Continue 가 한 버튼인 건 같은 질문이라서고, core 가 한 호출로
      답함. 스텝은 실행 중일 때 숨기지 않고 회색 — 나타났다 사라지는 컨트롤은
      찾아다녀야 하는 것. evaluate 필드는 정지 상태에서만 활성(식은 **프레임**
      안에서 평가되고, 달리는 프로그램엔 물어볼 정지된 프레임이 없음).
    → 하단 영역이 두 가지를 담게 됨 → Terminal / Debug 탭. 세그먼티드 컨트롤이
      아니라 불 켜지는 두 단어: 헤더가 28pt 인데 이미 셸 칩·+·닫기를 이고 있고,
      그 높이에 테두리 컨트롤은 자기가 앉은 행보다 큼.
    → 세션이 시작되면 패널이 앞으로 나옴. 끝날 때는 안 돌아감 — Start 눌렀는데
      터미널이 나오는 건 패널이 물은 것에 답을 안 하는 거고, 프로그램이 끝나는
      순간 터미널로 튕기는 건 패널이 '너 다 읽었다' 고 정하는 것.
    → **core 결함 하나 고침**: 프레임을 선택하면 이제 에디터가 따라감.
      select_frame 이 current_path/current_line 을 옮겨놓고 아무에게도 안 알려서,
      변수는 바뀌는데 사용자는 그 프레임을 볼 수 없었음. 어느 디버거에서든
      콜스택에서 프레임을 클릭하는 게 '거기 가서 보는' 방법임.
      dap_apply_stopped_location 은 이미 있었고 다른 파일도 열 줄 알았음. 플래그 하나.
    → Debug 메뉴에 디버거의 다섯 키. SwiftUI KeyEquivalent 는 함수키에 이름이
      없음 — AppKit 이 private-use 영역에 둠(NSF1FunctionKey = 0xF704) — 그래서
      숫자가 번역의 전부고, 이게 없으면 다른 단축키는 다 되는데 정작 사람들이
      누르는 다섯 키만 없는 메뉴가 됨.
    → 검증: 어댑터를 붙이려면 어댑터가 설치돼 있고 그 안에서 멈출 프로그램이
      있어야 하므로, 프로토콜이 아니라 **경계**를 고정함 — ffi 테스트 8개.
      idle 도 스냅샷으로 답하는가, fingerprint 가 움직여야 할 때 움직이고 아닐
      때 가만있는가, 변수 펼침이 fingerprint 를 움직이는가, 콘솔이 꼬리를
      나르는가, 상태줄이 error > hint > reason 순인가, 프레임 선택이 에디터를
      부르는가, 스택이 온전히 건너는가, 모르는 verb 가 아무것도 안 하는가.
    → 남은 것: 실제 어댑터로 굴려본 적은 없음(codelldb/debugpy 설치 + 멈출
      프로그램 필요). watch 표현식 목록과 예외 브레이크포인트 UI 도 없음 —
      core 엔 exception_filters 가 이미 있음.
}

✅ 10. 왼쪽 사이드바 git ui 개선 {

      폴더(뒤에 흐리게, 앞에서 자름) · 오른쪽 상태 칩. 루트 파일이면 폴더 생략.
    → 히스토리가 Text(g.line) 이었음 — FFI 가 "{strip} {short} {subject} {when}"
      으로 미리 이어붙인 문자열. 커밋이 경계에서 눌려서 face 에 재료가 없었음.
      short/subject/when/refs/lane color 를 따로 건네고 레인 색 점 + 제목 +
      해시·날짜·refs 로 그림. subject 가 compositor 에서 56자로 잘리고 있기도
      했음(자리가 있어도 못 보여줬다는 뜻).
    → 그래프 스트립은 네비게이터에 일부러 안 그림 — 모든 행이 monospace 로
      정렬돼야 그래프로 읽히는데 240pt 가 그걸 제목과 동시에 못 줌.
    → 미푸시 커밋 목록(Xcode 의 U 배지) 넣음. 계획은 "위 ahead 개에 배지"였는데
      그게 틀렸음 — 사이드바 워크가 git log --all --date-order 라, 한 시간 전에
      푸시된 동료의 팁이 내가 안 푸시한 두 커밋 위에 앉음. ahead 는 세지, 지목하지
      않음. 그래서 core 가 답이 이름 목록인 질문을 함: git rev-list @{u}..HEAD.
      GraphRow.unpushed 가 개수가 아니라 행마다 ABI 를 건넘 — face 가 틀릴 규칙
      자체가 없게. 업스트림이 없으면 rev-list 가 실패하고 아무것도 안 찍힘(= ahead
      가 그 브랜치에 대해 이미 보고하는 답).
      History 헤더는 찍힌 행 수를 셈. 커밋을 세면 그래프 limit 을 보고하는 건데
      그건 설정임.

✅ 19. 깃 워크벤치 changes 에 + - 에 색 구분이 없어. 그리고 세로 스크롤에 좀 여백을 두면 좋겠음. 맨 아래로 스크롤하면 맨 아래에 있는 파일을 열었을 때 적당히 중간쯤에 올 정도로 여유?

✅ 왼쪽 사이드바에서 여는 터미널에 문자가 안쳐진다
     → 독 터미널이 키보드를 딱 한 번, 뷰가 처음 마운트되는 그 순간에만 잡음.
       그것도 그때 호스트가 이미 창 안에 있어야만:
           guard host.mount(term) else { return }   // 이후로는 전부 false
           host.claimKeyboard(for: term)            // window == nil 이면 그냥 return
       네비게이터 레일에서 디버그 영역을 열면 withAnimation 안에서 들어오니까,
       트랜지션의 첫 updateNSView 는 representable 이 아직 창 밖일 때 돎. claim 이
       return 하고, mount 는 이미 arrival 을 소비했고, 다시 시도하는 코드가 없음 —
       셸은 돌고 그려지고 아무것도 못 받음, 클릭하기 전까지.
     → 놓친 claim 을 기억했다가 viewDidMoveToWindow 가 마무리. 이미 마운트된 셸은
       core 가 터미널 포커스라고 하고 *아무도* 안 잡고 있을 때 되찾음(setDebugArea
       가 0.1초 뒤 stale 필드 포커스를 지우면서 앞선 claim 을 지웠음).
     → 같은 증상의 다른 두 경로:
       · openDebugTerminal 이 독을 손으로 열어서 core 포커스와 필드 포커스 제거를
         건너뛰고 focused = true. focused 가 구동하는 루트 컨테이너는 포커서블이
         아니라 SwiftUI 가 네비게이터의 Filter 에 키보드를 줬음. 20줄 아래 탭
         핸들러가 문서화해둔 바로 그 버그가 이 한 호출부에만 남아 있었음.
       · 네비게이터 모드 버튼들이 무조건 같은 짓을 함. 어떤 목록을 보여줄지는
         키보드를 누가 갖는지에 대한 진술이 아님.

✅ 20. 3D 워크벤치 — glb/gltf·fbx·스키닝, 씬 그래프, 인스펙터, 익스포트

     ── .dae 가 안 그려지던 진짜 이유 ────────────────────────────────────
     지오메트리는 멀쩡했음: 정점 8281, 삼각형 16200, 인덱스도 범위 내.
     같은 source/element 로 SCNGeometry 를 새로 만들고 새 머티리얼을 붙이면
     완벽하게 그려짐. **머티리얼이 전부였음** — diffuse 와 transparent 가 둘 다
     /job/comms/.../loremipsum.png(남의 렌더팜 절대경로)를 가리키고
     transparencyMode 가 .rgbZero. 못 읽는 transparent 채널은 검정으로 샘플되고,
     RGB_ZERO 에서 검정은 완전투명 → 메시가 통째로 사라짐.
     → 이건 이 파일 하나의 문제가 아님. 절대경로 텍스처는 모든 DCC 툴의 기본
       동작이라 **다른 기계에서 온 모델은 전부** 이걸 밟음. 조용히, 그리고 정확히
       "뷰어가 고장난 것처럼" 보이면서.
     → 고침: 모델 옆 · textures/ · maps/ · images/ 에서 같은 파일명 먼저 찾고,
       못 찾으면 그 채널의 항등값으로 대체(노멀은 flat, 러프니스는 중간, AO 는

     · 프레이밍이 모델이 아닌 노드까지 포함. B389_loop.dae 는 1유닛 메시 옆에

✅ 새로운 이슈5. "cargo build ok but binary not found: target/debug/test" — 해결.
     정확한 보고였음. 절대 그 바이너리를 만들 수 없는 빌드였던 것.
     test.rs 가 카고 **워크스페이스** 루트에 놓인 헐렁한 파일임. 루트 Cargo.toml 은
     [workspace] 뿐이라 [package] 이름이 없음 → parse_cargo_name 이 None →
     파일 이름으로 추측해서 target/debug/test 를 기대함. 그리고 cargo build 는
     멤버 크레이트를 다 빌드하고 **성공함.** 요청된 것만 빼고.
     → RustBuild::of 가 소스에서(작업 디렉터리가 아니라 — 헐렁한 파일은 이 둘이
       바로 그럴 때 다름) 위로 걸어서 판단함: [package] 가 있고 그 src/ 아래에
       있으면 Cargo, 아니면 Rustc. 자기를 주장하지 않는 매니페스트에서 걸음을
       멈춤 — 그 위의 매니페스트는 이 파일과 상관없는 물건임.
     → 단일 파일은 rustc -g --edition 2021 로 컴파일해서 그걸 디버그함.
       (에디션을 안 주면 2015 라서 async·dyn·배열 IntoIterator 가 다르게 굴고,
        사용자가 쓴 것과 무관한 이유로 컴파일이 깨짐.)
     → 에러도 rustc 의 첫 error 줄을 고름. 마지막 줄("aborting due to N previous
       errors")은 사람이 할 수 있는 게 없는 문장임.
     검증: 유효한 단일 파일 → 컴파일·실행·디버그 가능한 바이너리. 사용자의
     test.rs → "error[E0015]: cannot call non-const function `godddddd` in
     constant functions" (line 8). 테스트 셋 3개.

☐ 24. 디버깅이 에디터에 보이게 (Xcode 네이티브 방향)
     (사용자: "보통 디버깅하면 에디터엔 표기되는 게 없고 디버거 패널에서만 보이는데,
      나는 이게 에디터에 시각적으로 보여야 한다 생각함".)
     → 설계 docs/SUISEI-DEBUG-IN-EDITOR-PLAN.md.

     · **절반은 이미 만들어져 있음.** 브레이크포인트는 거터에 그려짐(사인 비트
       0x40, 줄번호 뒤 노란 칩). 그런데 **멈춘 줄은 아무 데도 안 그려짐** —
       데이터가 없어서가 아님. core 가 이 호출자를 위해 접근자까지 써놨음:
         /// Stopped line if the session is currently stopped in `path`.
         pub fn current_line_for(&mut self, path: &str) -> Option<usize>
       아무도 안 부름. ABI 도 이미 건너감(current_path/current_line/has_location →
       Swift 의 DapSnap 까지 디코드됨). **픽셀 한 줄 앞에서 죽어 있음.**
       이번 세션 내내 나온 그 패턴의 한 단계 더 간 버전.

     · 애플이 실제로 하는 것과 그 밑의 원칙:
       멈춘 줄에 초록 띠 + 거터에 **꽉 찬 화살표** · 콜스택에서 부모 프레임을
       고르면 **빈 화살표** · 호버하면 값이 뜨는 데이터팁(디스클로저로 구조체
       안까지) · 브레이크포인트는 페넌트, 거터 밖으로 드래그하면 삭제,
       ⌘클릭하면 비활성 · 점프바가 프레임 이름을 말함.
       → **에디터는 "내가 어디 있나" 에 답하고, 패널은 "무엇이 참인가" 에 답함.**
         위치는 공간적이고, 앱에서 공간적인 표면은 에디터뿐임. 값은 공간적이지
         않음 — 그게 붙은 것을 가리키기 전까지는. 데이터팁이 바로 그 가리킴.

     · 거터는 **색이 아니라 모양**으로 말해야 함. 그 줄은 이미 git 바가 색을
       가져감(추가 초록/삭제 빨강, 스테이지드면 채움). 색으로 말하면 서로 싸우고,
       Increase Contrast 와 색약 사용자에겐 애초에 안 통함.
     · 멈춘 줄 띠는 **캐럿 줄 워시(current_line 토큰)를 재사용하면 안 됨.**
       캐럿 줄은 *내가* 있는 곳이고 멈춘 줄은 *프로그램이* 있는 곳임. 둘이 같아
       보이면 에디터가 어느 쪽인지에 대해 거짓말하는 것이고, 실제로 자주 같은
       줄임. 새 토큰 debug_stop, 맨 뒤에 붙임(ThemeToken 규칙).
     · **데이터팁은 Quick Help 카드 재사용.** QuickHelpPopover 가 이미 테마
       적용됐고, 높이 재서 캡 씌우고, 코드 스팬을 모노로 그림. 멈춘 상태에서
       호버하면 LSP 문서 대신 **선택된 프레임에서 DAP evaluate** 를 물음.
       같은 표면, 다른 공급자. 여기서 제일 값어치 크고 제일 쌈 — 어려운 부분이
       다른 용도로 이미 만들어져 있어서.
     · 멈추면 **화면으로 데려와야** 함. 브래킷 마커(스팬 kind 254)가 "core 는
       상태 없이 두고 face 가 ~1초 플래시를 소유한다" 는 선례임. Reduce Motion
       이면 펄스만 끄고, 정보는 띠와 화살표가 지고 있으니 그대로 읽힘.
     · 인라인 값(VS Code 의 줄 끝 회색 `x = 5`)은 **맨 마지막.** 정직한 비용:
       보이는 줄마다 변수마다 evaluate, 그걸 **스텝마다** 다시. 새 스팬 kind 도
       필요하고 소프트랩과도 싸움. 예산 합의부터.
     · 잊힐 것 하나: 색 띠로만 존재하는 멈춘 줄은 **VoiceOver 에 안 보임.**
       캔버스에 접근성이 아예 없는 상태고(별도 항목), 하필 이 기능은 목적 자체가
       "에디터가 네가 어디 있는지 말해준다" 임. 최소한 멈춤을 알리고 그 행에
       레이블은 줘야 함.

     · **왕복 비용이 0이었음.** 설계 문서가 "보이는 줄마다 변수마다 evaluate,

     · 스톱 비트는 git 사인 바이트의 비어 있던 0x04 를 씀. 브레이크포인트 비트가

       아무 표시 없음(줄 번호만 맞춰 엉뚱한 행을 칠하는 게 제일 자신만만하게

        스테이지된 헝크 모든 줄에 진짜 브레이크포인트를 그린 적 있음).
     · UI 다듬기(사용자: "ui 가 좀 구린디"). 스크린샷에서 실제로 뭐가 나빴는지:
       – 띠가 **거터까지** 덮어서 15pt 안에 색이 셋 — 초록 띠 + 줄번호 + 호박색
         브레이크포인트 칩. 아무것도 안 읽힘. 띠는 **코드 것**이고 거터는 이미
         자기 어휘(변경 바, 칩, 화살표)가 있음 → 텍스트 영역부터 칠함.
       – 초록이 셌음(18% → 12%).
       – 콜스택이 `test::recursive_test::h78d59b0538fe2034` 세 줄이었음. 그
         꼬리는 컴파일러의 구분용 해시라 사람이 읽을 게 아님. 재귀 프레임 셋이
         **똑같은 해시 셋**으로 보이던 게 패널이 안 읽히던 이유의 절반.
         → 잘라냄. 길이가 판별 전부고 정확해야 함: 레거시 러스트 맹글링은 h +
           **16자리** 16진수라, `mem::h64` 는 h64 라는 함수고 이름을 지켜야 함.
           "h 다음 아무 16진수" 로 썼더니 그걸 먹었고 **테스트가 즉시 잡음.**
           디맹글러가 아니라 표시용이라, 모르는 이름은 반쯤 먹지 말고 그대로.
       – 섹션 헤더가 내용과 같은 필드에 떠 있어서 세 패인이 한 덩어리 회색
         목록으로 읽혔음 → 대문자 + 트래킹 + 옅은 띠, 모델 워크벤치의
         WBSection 과 **같은 타이포그래피 언어**(앱에 언어가 둘일 이유 없음).
       – 변수 행이 "depth 0 unsigned int" 처럼 정렬 안 된 텍스트 셋이었음 →
         타입을 뒤로 보냄. 타입은 값이 *무엇인지*지 값을 읽는 일부가 아님.

       git 바이트엔 남는 비트가 없었고, 디버거의 두 사실이 서로 다른 필드에 살

     · 멈춘 상태에서 식별자에 포인터를 올리면 값이 뜸. **멈췄을 때만** — 돌고 있는

         pending 플래그가 영원히 서서, 값이 있을 리 없는 키워드 위에서 스피너가

       옮겨간 뒤라, 값만 오면 엉뚱한 식별자 밑에 붙음 — 맞는 답처럼 보이는 틀린
       답. refreshHover 가 "묻기 전에 지운다" 고 적어둔 것과 같은 규칙.
     · 드웰 0.45초. 한 줄을 가로지르면 식별자를 여럿 지나는데 매번 팝오버가

     · 카드는 Quick Help 의 **크롬과 타입**을 공유하고 **본문은 공유 안 함.**

✅ 새로운 이슈7. 85번 줄 더블클릭했는데 87번에 브레이크포인트가 생김 — 해결.
     둘이 겹쳐 있었음.
     · **거터가 mouseDown 마다 토글함** → 더블클릭 = 토글 둘. 그 사이에 어댑터가
       답하는데, 어댑터는 브레이크포인트를 **코드가 있는 다음 줄로 밀 수 있음**
       (85·86 은 주석, 87 이 코드). 그래서:
         클릭1 → 85 에 생성, 요청 전송 → 어댑터 "87" → 기록이 87 로 이동
         클릭2 → 85 를 토글 → 거긴 이제 없음 → **또 만듦** → 또 87 로 밀림 →
                 dedup 이 합침
       결과: **87 에 하나, 그리고 클릭한 줄로는 지울 수 없음.**
       순서로 못 고침 — 한 가지를 뜻하는 제스처는 한 번 발화해야 함.
       → 거터에서 clickCount > 1 은 무시. 더블클릭은 **하나의 제스처**.
     · **그리고 미는 걸 아무도 말 안 했음.** 클릭한 데서 두 줄 아래에 마크가 뜨면
       디버거가 옳게 군 게 아니라 **에디터가 틀린 것처럼** 읽힘.
       → "● breakpoint 85 → 87 (no code on 85)" 을 콘솔에 한 줄.
         **안 움직인 브레이크포인트는 아무 말 안 함** — 검증될 때마다 떠들면
         정작 중요한 그 한 경우가 파묻힘. 테스트가 둘 다 지킴.

     · 관찰(아직 안 함): reveal 이 **캐럿까지** 옮김. 표시가 없던 시절의
       대용품이었는데 이제 띠가 그 일을 함. Xcode 는 캐럿을 안 옮김 — 옮기면
       사용자가 있던 자리를 잃고, 그대로 타이핑하면 그 줄을 편집하게 됨.

       ① **어디 사는가** — 정적. textDocument/documentHighlight 가 발생마다
          **kind(Text/Read/Write)** 를 줌. core 는 이걸 안 물음. 갖고 있는
          request_references 는 **틀린 요청**임 — 워크스페이스 전체 검색이고
          ("모든 호출자 찾기" 용), 프로젝트 스캔 값을 치르고, 읽기와 쓰기를
          구분 못 함. documentHighlight 은 한 파일 한 왕복이고 목적 자체가 이것.
          → 첫 발생부터 마지막까지 바, 양 끝에 캡, **쓰기에 틱.** 읽기는 값이
            쓰이는 곳이고 쓰기는 값이 **움직이는** 곳임. 그 구분이 곧 기능이고
            응답에 공짜로 들어 있음.
       ② **언제 바뀌는가** — 런타임. **DAP 데이터 브레이크포인트(워치포인트).**
          이 기계에서 측정함:
            strings $(xcrun -f lldb-dap) | grep -i databreakpoint
            → dataBreakpointInfo / setDataBreakpoints / supportsDataBreakpoints
          **있고, 우리는 하나도 안 씀.** 정적 바는 값이 바뀔 *수 있는* 곳을
          보여주고, 워치포인트만 실제로 바뀐 곳을 보여줌. 이게 질문의 진짜 답.
          (같은 목록에 supportsSetVariable 도 있음 — 멈춘 상태에서 값 고치기.
           이 기능은 아니지만 역시 놀고 있음.)

     · **디버거 기능인 이유**: 멈춘 줄이 브래킷을 **둘로 자름** — 위는 이 값이
       이미 지나온 곳, 아래는 갈 곳. 디버거만 아는 사실이고, 공간적이고, 공간적인
       표면은 에디터뿐임. DEBUG-IN-EDITOR-PLAN 이 "변수 목록은 패널, 데이터팁은
       에디터" 라고 한 것과 같은 논거.

     · **놓을 자리가 문제.** 거터가 거의 참: [git 스트라이프][칩+줄번호][스톱
       화살표][코드]. 이번 세션에 이미 충돌 한 번 냈음(화살표를 git 레인에 놨다가
       텍스트 갭으로 옮김). → **코드 왼쪽 가장자리, 텍스트 안쪽**이 맞아 보임.
       이건 파일의 git 상태가 아니라 **코드에 대한 것**이라 코드 쪽에 속하고,
       거터를 한 픽셀도 안 씀. 스톱 띠와도 같은 가장자리에서 시작해서 자연스럽게
       겹침 — 바의 끊긴 자리가 띠 위에 정확히 떨어짐.

     · 정직한 비용: 심볼마다 왕복(디바운스 + (버전,심볼) 캐시 필수, 멈추지 않았을
       땐 아예 안 돌아야 함) · 400줄짜리 static 은 파일 전체에 바를 그림 = 정보가
       아니라 소음이니 보이는 밴드 + 여유로 잘라야 함 · **워치포인트는 하드웨어라
       희소함**(x86/ARM 넷). dataBreakpointInfo 가 가능 여부를 말해주니 물어보고
       제안해야 하고, 안 될 땐 이유를 말해야 함. 다섯 번째에서 조용히 아무것도
       안 하는 게 제일 나쁜 판본.

     ── ✅ V4 완료 (setVariable) ────────────────────────────────────────
     · **컨테이너를 주소로 씀, 변수 자신이 아니라.** DAP 의 setVariable 은 **부모의**
       variablesReference + 이름을 받는데, VarNode 의 var_ref 는 자기 **자식**으로
       가는 핸들임 — 관계의 반대쪽 끝. 트리가 행마다 depth 를 들고 평탄화돼 있어서
       컨테이너는 **바로 앞의 한 단계 얕은 행**임(로컬이면 Locals, user.id 면 user).
       테스트가 둘 다 확인함.
     · 답이 온 행을 갱신하고 **그 아래 있던 걸 버림.** 옛 값에서 읽어낸 것은 새 값에
       대한 설명이 아님. 새 variablesReference 가 오면 대놓고 그렇다고 말하는 거고,
       안 와도 자식들은 옛 값에서 읽힌 것임.
     · 그리고 **형제를 다시 읽음** — 같은 구조체의 다른 필드, 버퍼 옆의 길이가 같이
       움직였을 수 있음. 컨테이너 하나만 다시 읽으면 요청 하나로 끝나고 **트리 모양이
       보존됨**. 스코프를 다시 읽으면 사용자가 열어둔 게 전부 접힘.
     · 거절: 스코프는 값이 아님 / 돌고 있으면 설정할 프레임이 없음 / 못 하는
       어댑터는 아예 안 물음(메뉴 항목 자체가 없음 — 영원히 비활성인 항목은
       제품이 지키지 않는 약속).
     · 프롬프트가 지금 값으로 채워져 오고, **같은 값이면 편집이 아님** — 그대로
       두면 행의 자식을 버리고 컨테이너를 다시 읽는 값만 치름.

     · 단계: V1 구간 브래킷(documentHighlight, 디버거 무관, 단독으로 유용하고
       그리기를 증명) → V2 스톱에서 자르기(사용자가 물은 부분) → V3 워치포인트
       (E4 의 우클릭에 같이 붙음) → V4 setVariable.

     ── ✅ V3 완료 (워치포인트) ─────────────────────────────────────────
     · "값이 어떻게 이동하나" 의 **진짜 답**. 정적 브래킷은 값이 바뀔 *수 있는*
       곳을 보여주고, 워치포인트만 **실제로 바뀐** 곳을 보여줌.
     · 두 단계인 건 스펙이 두 단계라서고, **첫 단계가 중요한 쪽임**:
       dataBreakpointInfo 가 이름을 **프레임 안에서** 불투명한 dataId 로 풀고,
       "안 된다" 고 답할 수 있음.
     · **워치포인트는 희소한 하드웨어임** — x86/ARM 이 넷을 줌. 다섯 번째는
       거절됨. 먼저 물어보는 이유가 그거고, **거절을 삼키지 않고 말하는 것**이
       이 기능에서 제일 중요한 부분임. "다섯 번째에서 조용히 아무것도 안 하는 게
       제일 나쁜 판본" 이라고 설계 문서에 적어둔 그것.
     · 무장은 setDataBreakpoints 가 **집합 전체를 교체함** — setBreakpoints 와
       같은 모양이고, 목록이 단위인 이유. 그리고 어댑터는 info 에서 허락한 걸
       arm 에서 거절할 수 있음(하드웨어는 arm 때 잡힘) → 그 응답도 확인함.
     · **세션과 함께 죽음.** dataId 는 이제 없는 프로세스의 주소임. 다음 실행으로
       들고 가면 쓰레기를 무장하는 것.
     · 메뉴는 **변수 위에** 있음(우클릭). 어느 변수인지 되묻는 메뉴가 아니라.
       어댑터가 못 하면 **회색이 아니라 없음** — 영원히 비활성인 항목은 제품이
       지키지 않는 약속임. 스코프("Locals")에도 없음 — 값이 아니라 주소가 없음.
     · 테스트 6개: 먼저 묻는다 / 거절은 이유와 함께 보고된다 / 승낙은 집합 전체로
       무장된다 / 같은 값을 또 누르면 그만 본다 / 세션을 못 넘긴다 / 못 하는
       어댑터는 아예 안 묻는다.

     ── ✅ V2 완료 (스톱에서 자르기) ────────────────────────────────────
     · 멈춘 줄이 브래킷을 **둘로 자름.** 위 = 이 값이 **이미 지나온** 곳,
       아래 = **갈** 곳. 이 그림에서 디버거만 아는 유일한 사실이고, 범례 없이
       읽힘 — 그게 애초에 이걸 패널이 아니라 에디터에 그리는 논거였음
       (위치는 공간적이고 패널은 공간이 아님).
     · 미래 쪽은 **옅게.** 같은 브래킷, 같은 자리, 잉크만 덜 — 아직 안 일어난
       일이고, 그걸 무게로 말하면 두 번째 모양을 만들 필요가 없음.
     · ABI 변경 없음. 면이 이미 둘 다 알고 있었음(inValueExtent 와 isStoppedLine).
     · 가장자리를 다 재봤음: 중간이면 둘로 쪼개지고(멈춘 행이 틈), 세션이 없으면
       하나(평범한 브래킷), **첫 행에 멈추면 전부 미래**, **마지막 행에 멈추면
       전부 과거**, 한 줄짜리 구간이면 하나. 자기 캡과 맞물려 잘린 브래킷은
       모서리가 깨진 브래킷일 뿐이라 그 경우는 안 쪼갬.

     ── ✅ V1 완료 ───────────────────────────────────────────────────────
     · core 가 textDocument/documentHighlight 를 물음(전엔 아무도 안 물었음).
       파서는 발생마다 kind 를 읽음 — 1 Text / 2 Read / **3 Write**. 3 만 쓰기고,
       그 구분이 기능의 전부임.
       테스트가 두 가지를 지킴: kind 가 **없으면 쓰기가 아님**(스펙상 Text), 그리고
       **다음 발생의 kind 를 이 발생 것으로 읽지 않음** — 그러면 읽기가 쓰기로
       둔갑함. 그래서 각 발생을 자기 객체 안으로 잘라서 봄.
     · 요청은 **단어당 한 번.** 프레임 펌프에서 부르는데, 가드가 (버퍼 버전, 행,
       단어) 라서 단어 **안에서** 움직이면 아무것도 안 묻고 가만히 있어도 안 물음.
       이번 세션 내내 키당 O(파일) 을 걷어냈는데 여기서 되돌려놓으면 안 됨.
     · 그림: **코드 왼쪽 가장자리, 텍스트 안쪽.** 거터는 이미 참(git 스트라이프 /
       칩+줄번호 / 스톱 화살표) 이고 이번 세션에 그 충돌을 한 번 겪음. 이 마크는
       파일의 git 상태가 아니라 **코드에 대한 것**이라 코드 쪽에 속함.
       모양은 git 변경 바 그대로 — 캡 달린 바. 사용자가 이미 "이 구간, 한 덩어리"
       로 읽는 마크라, 같은 뜻에 새 어휘를 만들 이유가 없음. 쓰기는 **두꺼운 틱**.
     · 바는 발생이 없는 행도 **지나감.** 구간은 값이 *사는* 곳이지 값을 언급한
       줄의 목록이 아님. 테스트가 그걸 단언함.
     · 400행 넘는 구간은 **안 그림.** 400군데서 쓰는 static 이 화면마다 바를
       그리면 정보가 아니라 소음임. 아무 말 안 하는 게 "어디에나 있음" 보다 나음.

     ── V1 후속 (사용자 지적 넷) ────────────────────────────────────────
     · **"디버그 콘솔 열려있을때만"** — 브래킷·호박색 띠·호버 값 전부 디버거가
       말하는 것임. 게이트를 **core 에, 일하기 전에** 뒀음 → LSP 요청도 안 나가고
       스캔도 안 함. 기준은 dap.panel_open, 디버그 탭이 이미 세팅하는 값
       (한 사실에 출처 하나).
     · **"브라켓 디자인 구리지 않니"** ①: 행마다 사각형 + 양 끝 가로 발 = **자로
       그은 [**. git 바 주석이 그 실수를 이미 적어놨음 — "바는 헝크 모양 물건이고
       행 루프는 행 모양. 행마다 그렸더니 줄마다 캡이 붙었다." 똑같은 짓을 했음.
     · **"텍스트량 겹침 / 한칸 탭됐는데 왜 저기 그려짐"** — 스크린샷 둘이 같은
       결함의 양쪽임. 들여쓰기 없는 줄에선 스파인이 첫 글자에 얹히고, 들여쓴
       줄에선 코드에서 멀어짐. **고정된 x 는 내용이 들여쓰기 따라 시작하는 열에서
       살 수 없음.** → gutterTextGap(줄번호와 코드 사이 12pt, 스톱 화살표 지우고
       비어 있음)으로. 들여쓰기가 어떻든 모든 행에서 같은 자리.
     · **"걍 직선이잖아 / 모서리 둥글게"** — 직선은 "이 행들에서 뭔가 일어난다"
       고 말하고 브래킷은 "이 행들이 한 덩어리다" 라고 말함. **팔이 그걸 닫음.**
       스트로크 패스 + 스파인으로 들어가는 1/4 원호 + 둥근 캡. 꺾이는 부분이
       손으로 그린 것과 자로 그은 것을 가르는 지점임. Metal 경로는 사각형밖에
       없어서 모서리를 세 단으로 계단 냄.
     · **"렌더 불안정 / 화살표가 세로선 중간에 끼고 / 기존 세로선이 남음"** —
       증상 둘, 원인 하나. run 모양 물건을 **dirty rect 로 잘린** 행 루프 안에서
       조립하고 있었음.
         – 부분 리페인트가 **부분 run** 을 봄 → top/bottom 이 리페인트가 우연히
           시작·끝난 자리로 잡히고 **팔이 거기 그려짐**(그게 "화살표").
         – 캐럿이 다른 함수로 가면 옛 행들이 새 행들 근처에 없어서 아무도
           무효화 안 함 → 옛 스파인이 남음.
       → gitBars 처럼 **밴드 전체를 도는 자기 패스**로 모음(클립은 그리기에만
         계속 적용 — dirty rect 밖 행은 안 바뀌었고 이미 화면에 있음). 그리고
         브래킷이 자기가 그려진 자리를 기억해서 **있던 자리 ∪ 갈 자리**를
         무효화(setDatatipToken 과 같은 모양).

☐ 26. Logic View — 코드가 아니라 프로그램의 논리를 탐색하는 인터페이스
     (사용자 사양. 원문 요지 아래, 설계 docs/SUISEI-LOGIC-VIEW-PLAN.md.)

     ── 사용자 사양 ──────────────────────────────────────────────────────
     · 단일 파일을 플로우차트로 바꾸는 게 아니라, **프로그램 전체의 논리 구조를
       계층적으로 탐색**하는 네이티브 코드 이해 인터페이스.
       목표: 소스를 직접 따라가지 않고도 프로그램이 어떤 논리로 도는지 이해.
     · 정적 분석(AST · Control Flow · Call Graph · Symbol Resolution)으로 만들고,
       **디버거와 연결해 실제 실행 흐름까지** 표시.
     · 노드 종류:
       – **Process Node** — 변수 변경 / 계산 / 함수 호출 / 데이터 변환 / 상태 변경.
       – **Decision Node** — if·else / match / switch / loop 조건 / 에러 분기.
         분기 방향이 실제 코드의 조건과 연결됨.
       – **Flow Edge** — 단순 호출 관계가 아니라 **실제 control flow**.
     · **다중 파일**: 하나의 알고리즘이 여러 파일·모듈에 걸침 → 전부 펼치지 않음.
       기본은 **접힌 상태**. 외부 파일/모듈로 가는 지점은 그 이름으로 표시하고,
       확장하면 내부 로직이 나옴.
         Project View → Module View → File View → Function View → Statement View
     · **런타임 통합**: 현재 실행 중 노드 강조 / 실제 지나간 경로 / 실행되지 않은
       분기 / 반복 실행 횟수.
     · **변수 통합**: 각 노드가 런타임 상태와 연결 — [Validate User] 밑에
       user.id = 123, permission = true 처럼.
     · **AI 통합**: 줄을 고치는 대신 **논리 구조를 대상으로** 변경 요청.
       AI 가 먼저 **Logic Diff** 를 만들고(예: Retry → Backoff→Retry→Success),
       승인하면 실제 소스를 수정.
     · 설계 원칙: Source Code → Program Logic → Runtime Behavior → AI Modification
       을 **하나의 흐름으로** 연결. 작은 함수는 세부를, 큰 프로젝트는 파일·모듈
       단위로 자동 추상화. **코드를 그림으로 바꾸는 기능이 아니라 프로그램의
       구조와 의도를 탐색하는 새로운 개발 인터페이스.**

     ── 지금 코드베이스가 답할 수 있는 것 (측정) ─────────────────────────
     · 입력 넷 중 **셋은 이미 있음**:
       – AST: syntax.rs::live_tree() — 파일당 살아 있는 tree-sitter 트리, 편집마다
         증분 재파싱까지 됨.
       – Call Graph: lsp.rs::request_call_hierarchy + CallItem + CallDirection
         (incoming/outgoing). 이미 배선됨.
       – Symbol: documentSymbol / workspaceSymbol 둘 다 이미 요청함.
       – **Control Flow: 트리 어디에도 없음.** 없는 건 하나고, 하필 어려운 그거임.
     · 그리고 알아둘 것 하나: **Outline 이 AST 기반이 아님.**
       compositor/scene.rs::build_outline 이 버퍼를 줄 단위로 훑으면서 `#`·`fn `·
       중괄호·들여쓰기를 찾는 **문자열 스캔**임(max_items 200). Logic View 는 그
       위에 못 세움 — 문자열 스캔은 호출과 "호출을 언급한 주석" 을 구분 못 함.
       대신 Logic View 를 제대로 만들면 Outline 이 덤으로 진짜 기반을 얻음.

     ── 핵심 판단 ────────────────────────────────────────────────────────
     · **CFG 추출기를 서른 개 쓰는 건 계획이 아님.** tree-sitter 는 CFG 가 아니라
       구체 구문 트리를 줌. 확장 가능한 모양은 **언어당 노드 종류 표** —
       "이 kind 들은 분기, 이건 반복, 이건 호출, 이건 탈출" — 새 언어가 모듈이
       아니라 표 한 줄이 됨. 하이라이터가 캡처를 TokenKind 로 매핑하는 것과 같은
       모양이고, 그래서 하이라이터가 서른 개 없이 서른 언어를 함.
     · **접힘이 기능의 전부이자 계산 가능성의 전부.** 프로젝트 전체 CFG 는 미리
       계산할 물건이 아님(모든 파일의 모든 함수, 키 입력마다 무효화). 기본 접힘 =
       **펼친 것만 CFG 를 만듦** → 다루기 힘든 분석이, 이미 파싱돼 있고 이미
       증분인 트리 위의 함수 하나짜리 작업이 됨.
     · **런타임 — 공짜인 것과 아닌 것을 갈라 말해야 함.**
       공짜: 지금 실행 중인 노드(current_line 이 이미 있고 에디터에 이미 그려짐) ·
       **호출 그래프 상의 경로**(콜스택이 정확하고 이미 디코드됨) · 노드의 변수
       (프레임 스코프가 이미 패널에 있고 데이터팁이 이미 프레임 안에서 이름을 품) ·
       노드에 브레이크포인트(조건·로그·on/off 까지 이제 있음).
       **공짜 아님**: 함수 **안에서 어느 분기를 탔는지** — DAP 는 실행 이력을 안 줌.
       셋 중 하나여야 함: CFG 상 경로가 하나뿐일 때 추론(자주 그렇고, 그럴 땐
       "추론" 이라고 말해야 함) / 스텝하며 기록(타이밍이 변함) / 계측(프로그램이
       변함). 반복 횟수도 없음(hitCondition 은 필터지 보고가 아님). 실행되지 않은
       분기는 위의 여집합이라 같은 한계를 물려받음.
       → **추측한 경로를 사실처럼 그리는 게 이 기능이 할 수 있는 최악의 실패임.**
     · **신뢰의 규율 둘**: 노드는 **자기 소스 범위를 정확히** 가리킬 것. 그리고
       **추출기가 이해 못 한 건 버리지 말고 불투명 노드로**("⋯ 3 statements").
       분기가 빠진 플로우차트는 없는 것보다 나쁨 — control flow 에 대한 자신만만한
       거짓말이고 사람은 그걸 믿고 행동함. (모델 뷰어가 반대편에서 도달한 같은
       규칙: 못 읽은 것과 비어 있는 것은 다른 반응이 필요함.)
     · **AI 방향은 사양과 반대로 뒤집어야 함**: 논리 변경을 만들고 소스를 역산하는
       게 아니라, **소스 패치를 만들고 그걸 논리로 렌더**할 것. 전자만 "승인한 것이
       착지한 것" 을 보장함 — 후자는 추상을 리뷰하고 그 번역을 적용하는 거라,
       번역에 모호함이 조금이라도 있으면 승인한 diff 와 쓰인 diff 가 다른 물건이 됨.

     ── ✅ L1 완료 (표가 진짜 문법을 감당하는가) ────────────────────────
     · **감당함.** 같은 추출기가 **표만 바꿔서** Rust·Python·JavaScript·Go·C 를
       읽음 — 양쪽 팔에 라벨 붙은 분기, 백 엣지 달린 루프, 나가는 엣지 없는 exit.
       새 언어가 모듈이 아니라 **표 한 줄**임.
     · 신뢰 규율 둘이 코드에 있음: 모든 노드가 **자기 소스 범위**를 가리킴 /
       표가 모르는 건 **Opaque 로 보임, 사라지지 않음**(unsafe 블록으로 테스트).
     · **덤프를 눈으로 읽어서** 결함 셋을 찾음 — 테스트는 하나도 못 잡았음.
       초록불만 보지 말고 출력을 보라는 근거:
       – `total += i` 가 Opaque. 표에 assignment_expression 을 넣었는데 Rust 는
         `+=` 를 compound_assignment_expr 라고 부름.
       – 루프가 자기를 `i` 라고 라벨링. for 의 named_child(0) 은 루프 **변수**임.
         헤더는 **본문 앞의 전부** — 문법이 조각을 뭐라 부르든 통하는 규칙 하나.
       – Rust 본문의 끝 표현식이 Opaque. 그건 **반환값**임. 언어 의미라 표의
         플래그로 넣고, Python 으로 새지 않는지 테스트가 지킴.

     ── ✅ L2 완료 (계층과 접힘) ────────────────────────────────────────
     · 파일은 **함수 목록으로, 닫힌 채** 열림. 그 아래는 **아무것도 계산 안 함** —
       함수 400개짜리 파일이 그래프 400개가 아니라 행 400개임. 그게 감당 가능성
       논거의 전부.
     · **expand 만이 그래프를 만듦.** 열면 그 함수의 본문이 한 단계 안쪽으로
       들어오고, collapse 가 도로 버림. 함수 자기 Entry 는 자기 안에 다시 안 그림.
     · **호출을 열면 호출당하는 쪽 본문이 나옴** — 사양의 "[Authentication
       Module] → expand → authenticate()" 가 그거임. 지금은 같은 파일 안에서만.
     · **모호하면 안 열림.** 이름은 해석이 아님 — 같은 이름 함수가 둘이면 어느
       쪽도 안 고름. 엉뚱한 `new` 를 여는 건 Opaque 규칙이 막으려는 바로 그
       자신만만한 거짓말임. 파일을 넘는 건 같은 기계 장치 앞에 정의 조회를
       붙이는 것(LSP).
     · 여기서도 테스트가 순진함을 잡음: 호출 이름을 라벨에서 `(` 앞 전부로 떼면
       `let a = helper(3);` 이 `let a = helper` 가 됨. **괄호 바로 앞 식별자**로.

     ── ✅ L3 + UI 완료 (런타임 오버레이 · 스파인 뷰) ────────────────────
     · 런타임은 **디버거가 이미 가진 사실만** 읽음. 지금 실행 중인 노드 = 멈춘
       줄을 품는 **가장 안쪽 행**, 그 둘레 = 지금 안에 들어와 있는 분기/루프,
       호출자 = 콜스택(정확함). 어댑터 왕복 0회.
     · **추측 안 함.** 어느 분기를 탔었는지·루프를 몇 번 돌았는지·안 돈 가지는
       DAP 에 없음 → L4 에서 "추론"이라고 적고 하는 일. 단 `if` 본문 **안에**
       멈춰 있으면 그 본문에 들어온 것 — 그건 추론이 아니라 범위임.
     · 분기의 팔이 **팔로 읽히게** 됨: 그래프의 엣지 라벨(YES/NO)을 행이 들고,
       중첩은 범위 포함으로 계산 — 빌더가 따로 유지할 구조가 아님.
     · **UI = 탭 하나짜리 페인.** FileKind::Logic(=7). 탭이 소스 경로를 들고
       있어서 코드/로직을 나란히 열 수 있음 — 이게 패널이 아니라 페인인 이유.
       ⌃⌘L. 행 클릭 = 다른 페인의 캐럿이 그 줄로.
     · 그림은 **스파인**: git 변경 바 · 값 브래킷과 같은 물건("이 구간, 함께").
       라벨은 소스 텍스트 그대로(JetBrains Mono), 종류는 **모양**으로(대비 증가·
       색맹), 런타임은 **앰버** — 에디터의 멈춤 띠와 같은 색이라 한 사실로 읽힘.
       설계 논거: docs/SUISEI-LOGIC-VIEW-PLAN.md §6a.

     ── ✅ U1~U4 완료 (레일 · 에디터 마크 · 런타임 경로 · 분기 피크) ────
     · **네 번째 인스펙터 모드.** 아웃라인 옆. ⌃⌘L(세 상태: 닫힘/다른 탭/이미
       여기). 페인은 강등되어 "Open Logic in a Pane" 으로 남음.
     · 레일은 **에디터가 이미 말하는 걸 말하지 않음** — 파일명·언어·배너 없음.
       위 단계들의 레일, 종류 모양, 잘린 소스 한 줄, 아웃라인과 같은 우측 줄번호.
       `Y`/`N` — 이 폭에서 두 글자 칩은 라벨 한 단어 값임.
     · **캐럿을 따라감**: 캐럿이 든 함수만 열고 나머지는 안 건드림(호출을 다
       따라가면 파일 전체를 짓게 됨 = 접힘이 막으려는 그것). 선택된 행은
       스크롤해서 보여줌 — 안 보이는 선택은 따라간 게 아님.
     · **에디터 마크**: 선택 노드의 첫 줄 띠 + 그 노드 자기 들여쓰기 열을 따라
       내려가는 가이드(액센트). 멈춰 있으면 **지금 들어와 있는 분기/루프**마다
       앰버 가이드 — 디버거가 절대 안 보여주는 사실이고 범위라서 정확함.
     · 마크는 **run 으로** 넘어옴(행 단위 아님). 행 루프 안에서 조립하면 값
       브래킷이 조각났던 그 실수 반복. dirty rect 리페인트 규율도 같이 —
       가이드는 40줄인데 캐럿은 한 줄이라 옛 가이드가 화면에 남음.
     · 레인 소유권: 게터 갭은 값 브래킷 것(고정 x 라 거기 삶). 로직 가이드는
       성질이 반대(본문 하나 = 들여쓰기 하나)라 **텍스트 열**에 삶. 안 부딪힘.
     · **디버그 패널 닫으면 앰버 마크도 같이 사라짐** — 코어에서 게이팅.
     · **레일 2차 정리(읽기 불편함 신고 반영).** 원인 둘:
       – 캐럿이 함수를 열기만 하고 **아무것도 안 닫아서** 읽고 지나간 파일이
         통째로 펼쳐짐 → 캐럿이 연 건 캐럿이 닫음. 규칙 하나: **독자가 손댄
         함수는 캐럿이 더는 관리하지 않음**(열든 닫든 양방향).
       – 40줄이 전부 같은 크기·굵기·색이라 눈이 쉴 데가 없음 → 위계를 장식이
         아니라 **타이포**로: 함수는 앵커(11.5 medium, 위에 여백), 스텝은 조용히
         (10.5, 0.6), 줄번호는 함수와 선택/호버에서만, 평범한 스텝 앞의 불릿은
         전부 제거.
       – **평범한 스텝 연속은 `N steps` 하나로 접음.** `let x = self.y;` 는
         로직이 아니라 텍스트고, 텍스트는 한 칸 왼쪽에 있음. 접힘은 선택
         때문에 절대 안 열림 — 캐럿 따라 리플로우하는 목록은 자리를 못 잡음.
     · **아이콘 충돌 정리**: 로직 탭이 왼쪽 레일의 Source Control 과 같은
       브랜치 글리프였음 → **LP(`smallcircle.filled.circle`)**. 행의 분기
       마커도 같은 이유로 순서도의 마름모로.
     · **분기 호버 = 두 팔이 코드 위에 뜸.** 한 줄만 봐서는 못 읽는 유일한 것이
       분기고, "여기서 나가는 두 길이 뭐냐"를 코드 위에서 답함. 초록/빨강 대신
       액센트 두 농도 — 게터에서 git 이 이미 그 둘을 쓰고, 빨간 띠는 diff 로
       읽힘. peek 은 자리가 아니라 **질문**이라 선택을 건드리지 않음.
     · 테스트가 잡은 것: 패널 게이트가 `early return` 이라 **분기 피크까지
       삼키고 있었음** — 분기에 대한 질문은 디버거가 열렸는지와 무관함.

     ── 단계 ─────────────────────────────────────────────────────────────
     L1 함수 하나의 노드 트리(언어별 kind 표 + 살아 있는 트리에서 CFG, 정적 뷰만).
        표 방식이 진짜 문법을 감당하는지가 여기서 드러남 — 안 되면 버리기도 쌈.
     L2 계층과 접힘(접힌 노드 아래는 아무것도 계산 안 함). 데모가 제품이 되는 지점.
     L3 런타임 오버레이(현재 노드 · 콜스택 경로 · 노드의 변수 · 노드의 브레이크포인트).
        전부 이미 있는 상태를 읽음. '공짜 아님' 목록은 빼고 없다고 표시.
     L4 추론 경로 — CFG 상 도달 경로가 둘 이상이면 그림에 **"추론"** 이라고 씀.
     L5 Logic Diff — 패치 먼저, 논리로 렌더.

     · 디버거는 번들이 아님. 오늘 버그가 그거였고, 우리가 lldb-dap 사본을 호스팅하면
       애플이 이미 업데이트하는 걸 하나 더 들고 다니는 것. debugpy/dlv/js-debug 도
       pip/go/npm 이 정본 — "호스팅" 이 아니라 "찾아주고 설치를 도와주는 행" 이 맞음.
       LSP 서버도 같은 논리.
     · **언어가 번들임.** 30개 중 아무도 30개를 다 안 씀. 기본 탑재(작고, 첫 실행이
       네트워크 없이 돌아야 하는 것): rust/python/js/ts/json/md/toml/yaml/html/css/
       c/bash/go/java — 다 합쳐 10MB 미만. 나머지는 다운로드 → 기본이 ~28MB 가벼워짐.
       swift(5.0MB)는 판단 필요 — 맥 에디터라서.
     · 기술 비용: 지금 문법은 컴파일된 러스트 크레이트. 런타임 로드하려면 언어당
       dylib + tree_sitter_<lang>() 엔트리포인트 + dlopen (Zed/nvim-treesitter 방식).
     · **일정을 결정하는 제약**: 받아서 프로세스에 로드하는 건 전부 서명 + 노터라이즈
       돼야 함. hardened runtime 의 library validation 이 막고, 그걸 끄는 건 다운로드
       하나와 앱 보안 태세를 바꾸는 것. → 우리 서명/노터라이즈/호스팅 파이프라인이
       이 기능의 진짜 비용이고, 목록 UI 는 제일 쉬운 부분임.
       (헬퍼 프로세스로 우회 가능 — 3D 임포터는 됨, 문법은 안 됨: 구문 파스는 키마다
        도는데 키마다 RPC 는 이 에디터가 지키려는 예산 그 자체임.)
     · 규칙 하나: **없는 컴포넌트는 기능을 낮출 뿐 깨뜨리지 않음.** 3D 없는 .fbx 는

       없는 편집 가능한 문서. core 가 이미 그렇게 동작함.
     · 단계: C0 jpeg 19MB(아키텍처 0, 제일 싼 15MB) → C1 컴포넌트 하나로 파이프라인
       증명 → C2 문법 전체 → C3 Components UI + 첫 실행 선택 → C4 툴링 행 → C5 3D.

       섹션으로 묶고(Platform Support / Other Components / Other Installed /

    · visible_at 이 캐시된 전역 목록을 clone(20k 에서 String 2,500개)하고, 8개
      보여주려고 보이는 이름 전부에 ScopeSymbol 을 만듦. 이제 빌려 쓰고, prefix 를
      내려보내서 매치 불가능한 심볼은 아예 안 만듦. 권위 있는 필터링은 여전히
      activate_with — may_match 는 할당만 피하면 되니 일부러 느슨하고 non-ASCII 는
      다 통과시킴.
    키당 컴플리션 2.67ms → 0.227ms (20k, unopt).

실시간 협업 설계 (위 **feature** 1번의 답) — 요지:
  · gh 로그인과 Suisei Cloud 로그인을 UX 는 한 화면, 인증은 완전 분리.
    gh 는 로컬 개발 도구고 권한이 훨씬 넓음. Cloud 로그아웃이 gh auth logout 을
    부르면 안 됨.
  · project.suiseiprj 에 멤버를 적지 말 것 — 파일 고쳐서 자기 권한 올릴 수 있고,
    merge conflict 로 꼬이고, GitHub username 은 바뀜. 파일엔 project_id 만.
    권한의 정본은 서버.
  · 역할 Owner / Admin / Editor / Viewer. "Hand over admin" 은 역할이 아니라
    소유권 이전 액션. Admin 은 자기보다 낮은 역할만 관리.
  · 서버는 역할이 아니라 capability 로 검사 (document.write, member.invite …).
  · presence: 편집은 즉시·순서보장·ACK, 마우스는 움직일 때만 8~12Hz latest-only,
    300ms 멈추면 중단. 받는 쪽에서 80ms jitter buffer + 120fps 보간.
  · 좌표는 화면 픽셀이 아니라 문서 기준 (byte_offset + affinity + at_revision).
  · 편집 채널과 presence 채널 분리, 큐 우선순위 edit > control > presence.
  · 불변식: 키 입력은 GitHub·인터넷·서버 ACK 를 절대 기다리지 않는다.

✅ 미니파이된 한 줄이 하이라이터를 멈춰세움 — 해결 (2026-08-18).

        같은 1 MB 를 4만 줄로   100 ms

      그래서 480바이트를 칠하려고 8MB 를 다 걸었음.
    → 둘 다 `wrap::ROW_BYTES` 에서 멈춤. 렌더러가 긋는 그 선.
      변환은 잘리는 자리에서 포기하고(`None` = 안 그려지는 곳), 쿼리는 행마다
      그려지는 접두사까지의 **바이트 범위**를 받음 — 보통 파일에선 붙어서 범위 하나가
      되니 값이 0이고, 긴 줄 하나가 있을 때만 쪼개짐.
    · 1MB 1.91s → 248ms, 8MB 17.4s → 2.0s. 남은 2.0s 는 tree-sitter 의 파스 자체고
      워커 스레드에 있음(`syntax_worker`), UI 는 안 멈춤.
    테스트 5개. 그중 벽시계가 아니라 **비율**로 재는 게 하나 — 같은 파일을 두 윈도우로
    파싱해서(미니파이 행 포함 / 미포함) 둘을 비교함. 파스 비용이 양쪽에 똑같이 들어가
    상쇄되므로 기계 속도에 안 흔들림. typing_latency 때 배운 것. 고치기 전 5개 중 4개가
    실패하고(비율 5.5배, 컷 너머 토큰 99,514개), 나머지 하나는 아래 줄들이 그대로인지
    보는 가드라 양쪽에서 통과해야 맞음.

✅ 분할 페인 간 포커스 전환 시 스크롤이 튐 — 해결 (2026-08-18). 두 겹.
   결정적 단서는 사용자가 준 한 줄: **"no wrapping 옵션 키면 귀신같이 사라짐."**

    [1] **단위가 틀렸음.** 페이스가 스크롤 위치를 이렇게 구했음:
            let v0 = floor(documentVisibleRect.minY / lineH)   // 시각 행
            engine?.scrollSync(line: v0, …)                    // → App::scroll (줄 번호)
        `minY / lineH` 는 클립 위에 **그려진 행의 수**고 `App::scroll` 은 **줄 인덱스**임.
        wrap 이 꺼져 있으면 두 수가 같음 — 그래서 안 보였고, 그래서 끄면 사라짐.
        켜면 동기화마다 코어의 위치가 진실에서 멀어지고, `park_focused_pane` 이 그걸
        저장하고, 돌아올 때 `visualY` 로 반대 변환을 해서 가 본 적 없는 곳에 놓음.
        · 그리는 건 멀쩡했음. 캔버스는 자기 클립에서 `nearestBufferRow(atY:)` 로
          변환해서 그림. 코어의 사본은 **페인이 복원될 때만** 읽히고, 그게 정확히
          튀는 순간 — 그래서 스크롤하는 동안엔 아무 징후가 없었음.
        · 변환 함수는 처음부터 있었음. `wrap_buffer_at` 주석에 "for turning a click
          or a viewport top back into a line" 이라고 적혀 있는데 viewport 쪽
          호출자가 **하나도 없었음**. 네 군데(스크롤 동기화 2, 미니맵 피드,
          클립 비교) 전부 변환하게 함.

    [2] **포커스 이동이 "뷰를 옮기라"고 말하고 있었음.** `load_focused_pane` 은 다른
        문서를 든 페인으로 갈 때 `restore_state_from_tab` 을 지나야 함(그래야 App 이
        그 문서를 듦). 그게 `ScrollIntent::Restore` 를 세우고 **아무도 안 내렸음**.
        페이스는 그 말을 듣고 `setClipTo` 로 클립을 정수 줄·정수 열에 다시 놓는데,
        그 페인의 클립은 줄곧 화면에 있었고 **정확한 위치를 가진 유일한 사본**이었음.
        포커스가 움직인다고 뷰포트가 움직이지는 않음 — 그 자리에서 의도를 지움.

    테스트 8개. 코어 3개가 시각 행↔줄 왕복이 역함수임을 못박고(wrap 을 끄면 항등이
    되는 것까지 — 이 버그가 오래 산 이유), 5개가 포커스 이동은 복원을 요청하지 않되
    **탭 전환은 여전히 요청하는지** 지킴. 그중 3개가 고치기 전에 실패. 892개 통과.
